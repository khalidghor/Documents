The Case for Intent

MERCHANT SERVICES · STRATEGY · ST-003

Our API is modern. That is not the problem.

It describes transactions; the next decade of payments is about intent. And we modernised the front door, not the house. The API we publish today makes the merchant’s code our decision engine: it decides whether to retry, whether to step up, what a timeout meant and which method really settled — and we never see it. Behind it, capabilities live inside engines, so every new one waits for the slowest release. Agents will read that contract as their user interface and route around whatever it cannot express. This volume names ten things the door gets wrong and five the house gets wrong, sets out the seven building blocks that replace them, states sixteen principles and three gates for moving faster, and shows how to get there without asking a single merchant to re-integrate this year. An architecture annex sets out the identity hierarchy, the execution plan and the boundaries that stop it becoming another orchestration monolith.

01Our API is modern. That is not the problem.

JPMorgan already publishes a payments API that would pass any checklist from ten years ago: REST resources, JSON, OAuth 2.0, versioned paths, webhooks, a sandbox. It is called the Commerce Payments API inside the building and the Online Payments API on the developer portal. It carries real volume and the team that built it built it well. This volume argues that it is the wrong shape for what comes next — and that adding fields to it will not change its shape.

The argument is simple enough to fit in one sentence. Our API describes transactions; the next decade of payments is about intent. A transaction is something that happened. An intent is something a customer, a merchant or an agent wants to happen, which the platform then pursues — across methods, rails, acquirers, retries, authentication steps and minutes or days — and proves it pursued well. Every capability the library has designed sits on the second model, and almost none of it can be expressed in the first. [J]

There is a second question one level down, and it is the bigger one. We have modernised the front door. Have we modernised the house? An API is only as modern as the platform it exposes. If a new method of payment needs changes in several processing engines, if a routing change needs a coordinated release, if a capability arrives as a new endpoint and another integration, and if a payment’s lifecycle depends on which engine processed it, then we have put a modern interface on fragmented processing. The next competitive battle will not be won by whoever has the most APIs. It will be won by whoever can introduce, configure, optimise and prove a new way to pay fastest. [J]

THE HONEST LIMITS OF THIS CRITIQUE, BEFORE ANY OF IT

Everything said here about the current API is taken from what JPMorgan publishes to developers: the portal’s overview, core-concepts and capabilities pages, and an open-source mock of the Online Payments API v2.7.0 that mirrors its public endpoints [S]. THE PATTERN UNDER ALL TEN

In every case the decision that matters is made in the merchant’s code, after our response, out of our sight: whether to retry, whether to step up, which method really settled, what to do about a timeout, whether to believe a fraud score. That is why the API looks simple and integrations look hard. And it means the most valuable data in payments — what was tried, what else was possible, and what happened — is created by our merchants and thrown away. [J]

05Why now: the agent reads the API

For twenty years the payments API had a human reader: a developer who read the guide, learned the quirks and encoded them once. The agentic era replaces that reader with software that reads the contract and acts on it in real time, on behalf of a consumer who is not watching.

WHAT AN AGENT NEEDS FROM AN APIWHY A TRANSACTION API CANNOT GIVE IT
A durable object it can create once and confirm when the consumer approvesThe transaction is created and decided in the same call
An outcome it can trust without reading a guide per methodThe same status means different things for different methods
A safe retry: same intent, idempotent, never a second chargeA timeout leaves nothing to retry against
A way to ask what it is allowed to do before tryingCapabilities and limits live in documentation and boarding, not in a queryable plane
A record of the authority it acted underThere is no mandate and no evidence record to attach it to

The protocols are arriving faster than the APIs beneath them. Google’s Universal Commerce Protocol is live in AI Mode and Gemini; OpenAI and Stripe’s Agentic Commerce Protocol is in market; Meta and Sierra announced the Personal Agent Protocol on 6 October with its payments extension unwritten; Visa and Mastercard both run agent programmes. Every one of them assumes a PSP that holds a durable payment object and makes the decisions behind it. Stripe has had that object since it introduced Payment Intents in 2019. PD-009 sections 01 and 11. [S]

THE COMPETITIVE SENTENCE, SAID PLAINLY

Stripe and Adyen did not win developers because their APIs are RESTful. They won because the API is the product: one object per purchase, decisions made behind it, and a new capability that arrives without a re-integration. A bank-owned PSP that offers a transaction API with a better rate card is competing on the dimension agents will care about least. [J]

COMMERCE INTENT IS ALREADY THE MODEL

The review of v1.1 named its biggest missing opportunity “intelligent commerce execution”: distinguish commerce intent, payment intent, payment execution, financial obligation and funds movement, so the platform can serve marketplaces, procurement, multi-pay-in, multi-beneficiary payments, agent purchases and real-time money movement. 07A Payment Intent — and we call it Payment

The first change carries most of the others. One durable object per purchase, created once, confirmed once, driven by the platform through as many Attempts as it takes, and reported as one thing.

RESOURCEWHAT IT ISWHO NEEDS IT
OrderThe commercial transaction, when the client has no order system of its own. OptionalSmall business, marketplaces, instalments
PaymentThe durable commitment to collect: amount, method, mandate, authentication context, capture method. Externally “Payment”; internally the Payment Intent state machine with fifteen states merchants never seeEveryone. Level one of the API
SessionA customer or agent interaction: checkout, terminal, link, agent. Absent when nobody is present — captures, refunds, merchant-initiated chargesAny surface with a buyer in the loop
AttemptOne execution of one operation — authorize, verify, incremental, capture, void, refund, reversal — with its parent, operation id, exec_id and canonical resultRead by advanced clients; written only by the platform

Three rules come with it. Intent is immutable; execution is versioned — changing how we try never changes what the payment meant. Authentication binds to the Payment, so a step-up carries forward to every later attempt instead of re-challenging the customer. An idempotency key is required on every mutating call, so a retry after a timeout returns the same Payment, never a second one. The external name is Payment because a name that describes the internal state machine would leak our complexity into every integration guide — Option A, decided 5 October. [A]

The memo proposes eight resources. Six already exist, under the same name or another, and the other two — PaymentExecution and Refund — are fields on the Attempt. Adopting its names would reopen Option A and give the library a second vocabulary for one model — the same call PD-008 made when Stripe’s names were proposed. [A]

WHERE THE MEMO GOES ONE STEP TOO FAR

The memo lists “card versus ACH versus RTP versus wallet” as a decision for the platform and calls cross-method optimisation the bigger prize. Half of that is right. The platform may decide which methods to offer, and in what order, in a Session it hosts; an agent may choose among the methods its mandate allows. Both are decisions with evidence. The platform may not move a customer from the method they authorised to another — a card to a bank debit, say — without them: consent is per method, and bank debits carry their own authorisation requirements. Across methods, optimisation happens when the methods are presented; once a payment is executing, it happens across rails. [J]

21The page to put in front of the executive team

The memo’s closing narrative, kept in its own voice where it was strongest and brought into the library’s vocabulary where it was not. It is written to be read aloud, and it takes about three minutes.

FROM API MODERNISATION TO PLATFORM TRANSFORMATION

JPMorgan has made real progress with a modern Commerce Payments API. But a modern API does not make a modern payment platform. Our challenge is no longer to expose processing through better endpoints. It is to introduce, configure, optimise and prove new commerce experiences, payment methods, capabilities and rails — continuously.

Much of our estate still reflects how payment processing was historically organised. Capabilities are spread across engines; lifecycles vary by product; a new capability can need coordinated changes across many components. That slows us down and makes a consistent merchant experience hard.

Our north star is an intent-driven, decision-centric, capability-based platform, built on seven ideas: the Payment, one durable intent to collect; execution plans and one lineage, so every decision, attempt, event and ledger entry traces back; the Decision Platform, which chooses and records why; the policy plane, which says what is permitted; the entitlement plane, which says what a client has bought; Payment Processing as a catalog of capabilities, each released on its own; and experimentation, so every claim has a control.

Two separations hold it together. The method a customer chooses is modelled apart from the rail money moves on. And one set of ten states describes every payment, whatever the method, while each rail keeps its own truth underneath.

A new method should not need another processing platform. A new rail should not need a new merchant API. A new capability should not need a coordinated release. A new optimisation should be configurable, measurable and reversible.

Agentic commerce makes this urgent. Agents bring new actors, delegated credentials, spending mandates and protocols. We should not answer with another isolated stack: agents are a channel onto the same Payment, decisions, capabilities and money movement.

Stripe’s Payment Intent is an API abstraction. We can make the Payment the foundation of an execution architecture that adds what a fintech cannot: bank-grade controls, multi-acquirer neutrality, our own liquidity and money movement, and — where the JPMMS–Chase firewall allows — issuer-side intelligence.

The ambition is concrete: introduce a new payment capability, make it available to selected merchants, test it on a controlled population, measure its incremental economic value and scale it — without redesigning the payment API or coordinating releases across the processing estate. That needs a change in how we work as much as in what we build: product teams owning capabilities and outcomes on a shared execution platform, rather than asking engineering to change processing systems.

We should be measured not by how many APIs we expose, but by how fast a new commerce idea becomes a production capability, how well every payment is executed, and how consistently we deliver across every method, channel and rail. We should not just modernise how merchants connect to JPMorgan. We should modernise how JPMorgan thinks, decides and executes payments.

Two edits from the memo’s text are deliberate. “Issuing-side intelligence” is qualified by the firewall, because D35 has not decided how much of it may cross. And “PaymentIntent” is “the Payment”, under Option A. [J]
